Build a tiny agent.
Carry it. Do the work. Delete it.

embedai is a source-first recipe for a personal, disposable AI agent harness. You choose the endpoint, model, credentials, and tools. The build produces one small terminal executable for the machine that needs help.

The idea

An agent is mostly a loop.

No framework, vector database, plugin protocol, or daemon. A conversation array and a loop: send context and tool descriptions, execute returned function calls, append their outputs, repeat until the model answers. embedai keeps that mechanism visible — the code is the explanation, and the small size is the feature.

You Should Write An Agent ↗

+ What it is useful for

  • One-off diagnostics or maintenance on a remote Linux server
  • A temporary assistant on a Raspberry Pi, lab machine, or rescue environment
  • Machines where installing Python, Node.js, and dependency trees is undesirable
  • Learning how little machinery an LLM tool-calling loop really needs
  • Prototyping a narrow, custom agent with your own tools and instructions
  • A starting point for a purpose-built internal harness

− What it is not

  • A hosted service or multi-user agent platform
  • A sandbox — shell and file tools run with the invoking user's permissions
  • A secure way to distribute a valuable secret
  • A replacement for approval workflows around destructive operations
  • A persistent assistant with long-term memory
  • A universal executable — build one artifact per OS/architecture

# Personal

Build with your own endpoint, model, key, and purpose. A prebuilt agent encourages somebody else's defaults.

# Ephemeral

Use a short-lived credential, do the job, remove the artifact, revoke the key.

# Hackable

Ordinary Rust and JSON. Add a tool by editing one file. Remove a capability by deleting it from the list.

Quick start

Four commands to a working agent.

Native builds need a current stable Rust toolchain. Containerized cross-compilation needs Docker or Podman. A JSON build config also needs jq.

build & run locally 
# clone and build with your own values
git clone https://github.com/butelo/embedai.git
cd embedai

./build.sh \
  --endpoint https://api.openai.com/v1 \
  --api-key sk-your-short-lived-key \
  --model gpt-5-mini \
  --output embedai

# embedded endpoint, key and model — no env vars needed
./embedai
build from a config file 
cp build.example.json build.json
# edit build.json, then:
./build.sh --config build.json

# build.json
{
  "endpoint": "https://api.openai.com/v1",
  "api_key": "sk-your-short-lived-key",
  "model": "gpt-5-mini",
  "target": "aarch64-unknown-linux-musl",
  "podman": true,
  "output": "embedai-linux-arm64"
}
cross-compile for an ARM device 
# static musl build — no cross-linker required
./build.sh \
  --endpoint https://your-endpoint.example/v1 \
  --api-key sk-your-short-lived-key \
  --model your-model \
  --target aarch64-unknown-linux-musl \
  --podman \
  --output embedai-linux-arm64

scp embedai-linux-arm64 user@device:/tmp/embedai
ssh user@device /tmp/embedai
scripts & terminal commands 
# it also works non-interactively
printf 'Report the current directory\n/quit\n' | ./embedai

# repoint an embedded binary without rebuilding
./embedai --endpoint http://localhost:8080/v1 \
          --model local-model

# terminal commands
/help   show commands and available tools
/clear  discard in-memory conversation context
/quit   exit

↻ Configuration precedence

CLI endpoint/model options → runtime OPENAI_BASE_URL, OPENAI_MODEL, OPENAI_API_KEY → values embedded at build time → defaults. The endpoint must implement POST /responses with Responses API function calling; a server offering only /chat/completions is not compatible.

Built-in tools

Five tools. No approval prompts.

Commands have a 30-second default timeout, tool output is bounded, and the model loop stops after 24 turns. These limits reduce accidents; they do not provide a security boundary.

shellRun a command through sh on Unix or cmd on Windows
read_fileRead a text file
write_fileCreate or replace a text file
list_dirList directory entries
pingUse the system's ping executable

~ Make it yours

The core is four small files. This is meant to be edited, not extended through a plugin API.

src/agent.rsResponses API calls, context replay, agent loop
src/tools.rsTool JSON schemas and implementations
src/config.rsEmbedded and runtime configuration
src/main.rsTerminal and command-line interface

Add a tool by extending tools::definitions() and tools::execute(). Change INSTRUCTIONS to give your harness a specific job. Delete shell for a narrower agent.

Portability

Build here. Run there.

Cross-compilation moves complexity to the builder: a static musl executable runs on a compatible machine without a language runtime, package installation, or TLS library setup. One artifact per OS/architecture — not one magical binary for every machine.

Rust targetTypical machine
x86_64-unknown-linux-muslIntel/AMD Linux, static

1 Build

Pass a target triple and a container engine — --docker or --podman. Prebuilt musl toolchains, no local cross-linker.

2 Carry

Copy with scp, serve it over HTTP, or use removable media. The container is only needed to build, never to run.

3 Clean up

Delete the binary on the target, remove local artifacts (cargo clean), then revoke or rotate the API key.

Trust is the hard part

Disposable credentials, not disposable caution.

Embedding a key solves deployment, not secrecy. Giving a model shell access solves flexibility, not safety. The harness favors explicit trade-offs over claims of security — anyone holding the binary can potentially extract its key or use its tools.

  • !Embedded credentials are recoverable. Use a short-lived key and revoke it afterwards.
  • !Tool calls run with your OS permissions. There is no sandbox around shell or file access.
  • !Prompt content can contain injection. Tool output and file contents reach the model.
  • !Timeouts and limits are reliability controls. They are not a security boundary.
  • !Deleting a binary cannot revoke a copied key. Rotate the credential when the task ends.
  • !The safest tool is the one not included. Remove capabilities you do not need.
Security guidance Design philosophy

The source is the product — not the binary.

Small enough to read and modify. Built for the one machine in front of you.
